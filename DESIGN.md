# Design: TravelAgentAI — The Decisive AI Travel Planner

## Problem Statement

You're planning a real trip ("Europe, December, 4 weeks") and you don't want a
wall of options. You want a travel pro to take what you want out of the holiday
plus your dates and just hand you the answer: which places to go, in what order,
and what to do there. TravelAgentAI is that pro.

The long-term vision is an all-in-one travel AI: plan, hunt deals, chat like a
concierge, and book. v1 is the **planning** tool. The architecture is one chat
agent with tools, so deals and booking become additional tools later, not
separate apps.

## What Makes This Cool

**It has an opinion.** Most AI trip tools (Mindtrip, Layla, Wonderplan, and just
asking ChatGPT) dump options and make you do the sorting. Yours returns one
strong, complete plan. Decisiveness is the personality.

The killer demo: broad input → full multi-city route. "Europe, December, 4 weeks,
mid-budget, food and history" produces a real route (which cities, in what order,
nights per city) plus per-day things to do. Single-destination ("I'm going to
Tokyo for 5 days") is just the easy subset of the same engine.

## Constraints

- Solo, personal, learning-first project. Success is measured by whether the
  builder would use it, not by users or revenue.
- Builder is an experienced vibe-coder (fluent directing Claude to write code),
  newer to agent architecture specifically. The build should lean into LLM
  orchestration and surface the 2-3 concepts worth genuinely understanding (not
  just generating), because an agent you don't understand is an agent you can't
  debug.
- v1 is planning only. No payments, no booking, no accounts.

## Premises

These were confirmed during the session:

1. **For-you-first.** Success = you'd genuinely use the output to plan your real
   December Europe trip. If you wouldn't follow the plan, it failed.
2. **v1 is planning only.** Deals and booking are real but later, and they plug
   into the same agent as tools.
3. **Decisiveness is the personality.** One strong plan (maybe with a swap or
   two), not a menu.
4. **Grounding beats polish.** A plain plan with real, correct places beats a
   beautiful plan full of hallucinations.
5. **Agent-with-tools is the destination**, because it's both what's worth
   learning and the backbone the all-in-one vision needs.

## The Central Technical Insight

The hard part isn't the LLM writing a nice itinerary. **It's grounding.** A pure
LLM planner feels magical for 30 seconds, then you notice it invented a
restaurant, got a train time wrong, and suggested an outdoor market that's closed
in December. The thing that makes this *good enough to actually use* is the agent
reaching for real data instead of trusting its own memory. That single idea is
why agent-with-tools is the right shape and not over-engineering.

## Approaches Considered

### Approach A: Prompt-first one-shot (minimal, fastest)
One strong structured LLM call. A small input feeds a heavy system prompt; the
model returns a structured itinerary; you render it. Effort: S. Risk: Low to
ship, Medium quality. Teaches structured output and prompt design. Ships in a day
or two. Weakness: hallucinates specifics, no real routing or live info.

### Approach B: Agentic tool-using planner (ideal architecture)
An agent loop: the LLM plans but can call tools (search real places, fetch
details, maps/distance for routing) and grounds the plan in real data. This is
the exact backbone deals and booking plug into later as more tools. Effort: M-L
(see Risks — the jump from A is bigger than it looks). Teaches agent loops, tool
calling, grounding.

### Approach C: Conversational refiner (creative/lateral)
Don't one-shot it. A short interview first, then the decisive plan. Feels most
like a real agent. Wraps around A or B. Effort: M (adds multi-turn state — see
Risks). Teaches conversation state. Weakness: slightly delays the instant-magic
moment, can annoy if it over-asks.

## Recommended Approach

**A now, evolve to B** (selected). Build the one-shot skeleton first to get a real
plan on screen and prove the loop, then graduate it into the agentic version by
adding the first real-data tool. Add C's clarifying questions last. This ships
something in days and walks straight into the agent architecture instead of
starting in the deep end.

## Architecture (v1)

**Recommended stack:** Next.js (App Router, TypeScript) + the Claude API via the
**Vercel AI SDK**, deploy to Vercel. Rationale: plays to your vibe-coding
strength, gives you a shareable URL, and the single API route is exactly where
tools get added in step B. The AI SDK is recommended specifically because it
handles streaming and tool-calling loops for you (both of which you need — see
Risks). A Python script is a fine alternative to start, but the web app is the
version you'd show off.

**Model:** v1 ships with `claude-opus-4-8` (the highest-quality planner) as the
single `MODEL` constant in the route. Switch it to `claude-sonnet-4-6` to cut
cost roughly in half for a small quality trade — sensible when running lots of
test calls. (Current Anthropic model IDs as of this doc; confirm against the
live model list, IDs rotate.)

**Structured output (as built):** instead of `output_config.format`, v1 forces a
single tool (`emit_itinerary`) whose `input_schema` is generated from the Zod
schema via Zod 4's native `z.toJSONSchema`. Forced tool-use is the most
version-stable way to get structured JSON back, and the same Zod schema validates
the response before it reaches the UI. Same contract, sturdier mechanism.

**Input (decided):** one free-text textarea. The user types their whole brief in
plain language ("Europe, all of December, 4 weeks, mid-budget, love food and
history, hate early mornings"). No structured fields in v1 — let the model parse
region-vs-city, dates, budget, and preferences out of the text. This is the
decisive-by-default call and it's less to build. Add structure later only if
parsing proves unreliable.

**API route (decided):** `POST /api/plan`, request body `{ brief: string }`,
response = the Itinerary streamed back. Use streaming, not a blocking response
(see Risks — a 4-week plan takes 10-30s and a blocking call will 504 on Vercel).

**The contract that everything hangs on — the itinerary schema.** Make the model
return structured JSON, not prose. Rough shape:

```
Itinerary {
  summary: string            // one-line "what this trip is"
  totalNights: number
  cities: City[]             // ordered = the route
}
City {
  name: string
  nights: number
  why: string                // user-facing: why this city, why this many nights
  days: Day[]
}
Day {
  date: string
  morning / afternoon / evening: Activity
}
Activity {
  name: string
  type: 'food' | 'sight' | 'transit' | 'rest' | ...
  why: string                // user-facing blurb (one sentence, why it's here)
  grounded: boolean          // false in step A; set true when verified in step B
  approxCostNote?: string    // OPTIONAL, omit in v1 — it's ungrounded and
                             // conflicts with premise #4. Add when the deals tool lands.
}
```

The `grounded` flag is the seam between A and B. In A everything is
model-generated (`grounded: false`). In B, the agent verifies named places via a
tool and flips the flag, and the UI can mark which items are confirmed real.

**Step A (build now):** input textarea → `POST /api/plan` → one streamed Claude
call with the schema as structured output → render the itinerary as it streams.
No tools yet. Everything is `grounded: false`.

**Step B (evolve):** turn the single call into an agent loop and add the first
tool: a place verify/search tool. Grounding granularity: the model proposes a
plan, then for each city it verifies the named places (batch the lookups per city,
not one API round-trip per activity — fewer calls, cheaper, faster). Flip
`grounded: true` on the ones that check out, drop or swap the ones that don't.
Add a maps/distance tool later so multi-city routes stay sane.

**What the agent loop actually is** (this is the concept worth understanding, so
here's the shape — it's not magic):

```
messages = [systemPrompt, userBrief]
loop:
  response = claude(messages, tools=[verifyPlace, ...])
  if response has tool calls:
      for each call: result = runTool(call)
      messages.append(response)          // the assistant's tool request
      messages.append(toolResults)       // your tool outputs
      continue                            // let the model react to the results
  else:
      return response                     // model is done, this is the final plan
```

You are maintaining a growing `messages` array across several API calls within a
single user request. That is the whole trick. It's an in-memory orchestration
layer, not a single API swap — budget for that (see Risks).

**The 2-3 concepts worth actually understanding (not just generating):**
1. **Structured output** — the itinerary schema is the contract between the LLM
   and the UI. Get it right and rendering is trivial. Getting Claude to reliably
   emit valid nested JSON takes prompt work — see Risks.
2. **The agent loop / tool-calling** — the pseudocode above. If you don't get
   this you can't debug the "why is it calling the same tool four times" failure.
3. **Grounding strategy** — what's real vs model-generated, and how you verify
   and mark it (the `grounded` flag).

## Risks / Gotchas (read before you build)

1. **Vercel free tier has a ~10s function timeout. A 4-week plan will blow past
   it and 504 in production even though it works locally.** This is the most
   predictable wall. Fix: stream the response (the AI SDK does this), and/or set
   the route's `maxDuration`, and/or deploy somewhere without the cap. Decide
   this on day one, not after the first failed deploy.
2. **Structured output is not free.** A 4-week trip is ~28 days × 3 slots ≈ 80+
   Activity objects of nested JSON. Claude will occasionally emit invalid or
   partial JSON early in prompt tuning. Use the SDK's structured-output / tool
   mode, validate with the Zod schema, and handle the parse-fail case (retry or
   show a clean error). Don't assume the JSON is always good.
3. **Lead with a FREE grounding tool, not Google Places.** Places needs a billing
   account and has per-request cost and quota setup that can eat a day. Start with
   Claude's built-in web search (or a free search API like Brave/Tavily, or
   OpenStreetMap Nominatim for place existence). Treat Google Places as a later
   quality upgrade, not the v1 dependency.
4. **Step A → Step B is a real jump,** because B means managing the messages array
   and the tool loop above. It's the fun part and the learning payoff, but it's
   more than "M effort" — give it its own focused session.
5. **Error/empty states.** The plan call can fail or time out. Even for a just-you
   app, add a loading state (streaming covers most of this) and a clean failure
   message so a 20s blank spinner doesn't look like a hang.

*(MCP = Model Context Protocol, a standard way to expose tools/data to an LLM.
Mentioned only as a future option for plugging in tools; ignore it for v1 and use
plain function/tool-calling.)*

## Open Questions

- City count for long trips: let the model decide, or cap/ask? (Lean: let it
  decide in A; one of C's clarifying questions can pin "deep vs broad" later.)
- Budget: keep it as free text the model interprets (decided for v1); revisit a
  structured band when the deals tool needs it.
- Live prices, saving/editing plans, accounts: all deferred to later tools/version.

## Success Criteria

- **v1 (done) — Approach A:** you type a real brief and get one solid, complete,
  structured itinerary streamed and rendered, even if not yet grounded.
- **v1.5 (the bar that matters) — reached at Next Steps Step 5 (Approach B):** you
  type your real "Europe, December, 4 weeks, [your prefs]" and the output is a
  plan you'd genuinely consider following, with real places that actually exist
  and a route that makes sense. Step 5 is the primary quality milestone, not an
  afterthought.

## Next Steps (build order)

1. Define the itinerary JSON schema as TypeScript types / a Zod schema. This is
   the spine; do it first.
2. Do The Assignment below (hand-write your real trip brief + ideal output).
3. **Approach A:** textarea → `POST /api/plan` → streamed Claude structured-output
   call → render. Get a plan on screen. Decide the Vercel timeout fix now (Risks #1).
4. Test on your real Europe trip plus 2-3 contrasting briefs (a short single-city
   trip, a tight-budget trip, a no-preferences trip). For each, write down every
   place it invents or gets wrong. **That failure list is the spec for Step 5** —
   it tells you exactly what grounding has to fix.
5. ✅ **Approach B (v1.5) — DONE.** Added a free place-verify tool (OpenStreetMap +
   Wikipedia, no API key) and converted the single call into the agent loop above
   (`lib/verify.ts` + the loop in `app/api/plan/route.ts`). Bounded to ~2 model turns for
   latency; verified places are badged "real" in the UI. Implementation note: grounding is
   attached by the server as a per-activity verdict (enriched `Verified*` types), not a
   `grounded` field the model fills — the verdict is ours, not the model's claim.
6. ✅ **Streaming — DONE.** `POST /api/plan` now returns a `ReadableStream` of
   newline-delimited JSON progress events instead of a blocking JSON response. The agent
   loop's natural phases become events: `drafting` → `verifying` (with per-place `done/total`
   from a callback threaded through `lib/verify.ts`) → `finalizing` → the final `itinerary`.
   Model calls use `client.messages.stream(...).finalMessage()` (no HTTP timeout on the big
   emit turn; `max_tokens` up to 64k for long trips), and a heartbeat keeps the connection
   alive during silent turns. The browser reads the stream and shows live progress, so it
   no longer hits the client/gateway timeout. (The server function's own wall-clock cap
   still applies on serverless — verification at ~1 req/sec is the floor.) Also hardened
   in the same pass: `verify_places` is now *forced* on turn 1 so a plan can't be emitted
   ungrounded; a token-overlap guard in `lib/verify.ts` stops loose geo matches from
   over-confirming fabricated places; per-lookup fetch timeouts; and server-side recompute
   of `totalNights`.
7. ✅ **Clarifying questions (Approach C) — DONE.** A cheap intake step
   (`POST /api/clarify`, on `claude-haiku-4-5`) decides whether to ask the traveler the two
   committed questions: **(a) "deep (few cities, more nights each) or broad (more cities,
   faster)?"** and **(b) "any must-include cities or hard no's?"** — but only when the brief
   leaves them open and they'd change the plan (a single-city brief gets asked nothing). The
   answers are replayed into the plan request as prior conversation turns, so the planner
   conditions on them. That's the multi-turn state: the prior Q&A lives in the messages array
   the loop already maintains.
8. ✅ **Ground the route — DONE.** Added a second grounding tool, `check_route` (`lib/route.ts`),
   so the agent loop is genuinely **multi-tool**. After `verify_places` grounds the *places*, a
   multi-city trip gets one turn to call `check_route`, which geocodes each city centroid via the
   existing Nominatim layer (`geocodeCity` in `lib/verify.ts`) and computes great-circle (haversine)
   leg distances, flags long hops, and 2-opt-suggests a tighter order when one clearly beats the
   model's. The model reacts (reorder / merge / drop) before the forced emit. Design choice: keep
   `verify_places` the *sole forced* tool on turn 1 (place grounding stays structural), then offer
   `{check_route, emit}` on an optional route turn for multi-city trips only (single-city skips it,
   keeping the 2-turn fast path); a new `routing` stream phase shows it live. Straight-line distance
   isn't travel time, but it reliably catches zig-zags — a real driving-duration API (OSRM) is a
   later upgrade, not a v1 dependency.
9. Then the rest of the all-in-one vision: deals, concierge chat, booking — each a new
   tool on the same agent.

## The Assignment

Before you write any code: by hand, write out the exact brief you'd give a human
travel agent for your real December Europe trip, and sketch what the perfect
itinerary back would look like (cities, nights per city, a handful of must-dos).

That hand-written pair is your first test case and your quality bar. You cannot
tell whether the AI is any good until you've decided what "good" looks like to
you. This is 20 minutes of writing that will save you days of building toward a
fuzzy target.
